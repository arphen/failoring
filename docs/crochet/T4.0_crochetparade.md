# T4.0 — CrochetPARADE spike

Spike for §5.0 of `docs/CROCHET_PLAN.md`: can CrochetPARADE be the crochet pattern front end?
Everything below was produced on 2026-10-16 on an Apple Silicon Mac (arm64, macOS 15.7.9,
node v26.10.0), against CrochetPARADE commit `06e987b13ccfc94cfdfcebc1fe4664d37d2c6687`
(GitHub). The layout runs are deterministic: the layout seeds its random starting positions
with `seed=0` unless the pattern sets `DOT: start=`, so every number here is reproducible.

**Outcome: recommendation B** — adopt CrochetPARADE and add a Failoring extension line for the
two things its grammar cannot express (second targets of through-both-layers stitches and
strap-end joins). See §7 for the decision-rule check.

### Constructs that needed a workaround, per fixture

**pouch.txt**

* Turned rows, edge labels, the border round over four edges, the strap on a rim subset — **no
  workaround** (`ch,15sc,turn`; `sc.L1`/`sc.R1`; absolute refs `sc@[51,30],4sc` = border
  positions 30–34 = front-rim sts 6–10).
* **Side seams (sc through both layers):** CrochetPARADE cannot express one stitch with two
  targets. The fixture works each seam sc into the rows-25-1 layer only (`sc@L25 … sc@L1`);
  the partner layer (rows 26–50) is deliberately unlabelled and unreachable — its stitches are
  the second targets the extension line must supply (§7). Two-stitch alternative exists in CP
  (second attachment head: `sc@L25,sc@1L26`; or a `DEF` composite), but that doubles the seam
  stitch count, so it was not used.
* **Fold** (`layout body fold rows 25|26`): not a graph construct in CP; nothing to transcribe.
  (CP can shape folds later via `DOT:` plane constraints; that is T5.3's concern.)
* **Strap end joined through `strap.row(80)` & back-rim sts 10–6:** only one target is
  expressible; the fixture emits 5 `ss` into back-rim positions 74…70 (plan sts 10–6). The
  strap row 80 side is the second target for the extension line.
* Front rim across `body.foundation`: the row-1 `sk` consumed the chain next to the hook
  (like "ch 2 from hook"), and that chain is not a stitch; the rim covers the 15 worked chains
  (`sc@[0,14],14sc`). Counts match; noted so the importer does not look for a 16th rim stitch.
* `fasten off` / yarn continuity: no CP construct; omitted (the plan says continuity is not
  simulated).

**bag_round_\*.txt (all five)**

* **Oval base ("working on the opposite side of the chain"):** CP has no second-side construct.
  The idiom `sk,49sc,3sc@[0,0],49sc,sc@[@],ss@[%,0]` parses with the plan's counts (102), and
  its structure matches the plan's chain arithmetic exactly: 1 chain consumed by `sk`, 48
  middle chains with 2 sc each, both end chains with 3 sc, the outermost chain unworked (the
  plan's ch 51 is unworked too). One deviation: CP works an unturned chain row from the tail
  chain upward (index 0 = the `sk` chain), so the two ends are chains 0 and 49 rather than 1
  and 50. Nothing references foundation-chain indices from later rounds, so this is invisible
  in the graph.
* Rounds + per-round join — **native** (`ss@[%,0]`: an sl st stitch that attaches to the
  round's first stitch).
* BLO round, FLO round, sl st round — **native** (`scbl`, `scfl`, `ssbl`; the next round
  attaches to those stitches directly, which is what the `slst` variant wants).
* **Surface sl st on the base:** CP has no surface-stitch type and no placement along a
  surface. The fixture writes it as a later row, `ss@[3,0],113ss`, attaching a chain of sl sts
  to round 3's stitches (no join). The graph is right; the 3D placement (lying on the surface,
  not stacked) is a T5.3 layout concern.
* `mark base`, `mark top`, `layout bag revolve`: not graph constructs (marks are not modelled;
  layout directives are T5.3). The fixture uses round numbers in absolute refs instead
  (`sc@[44,25]`, join `ss@[44,87]…[44,82]` = plan sts 26–31 and 88–83).
* Strap/end join: as the pouch (6 `ss` into top positions 87…82; second targets → extension).
* `fasten off`: omitted, as above.

**circle_plus6/5/8.txt, tube40.txt** (step-5 tests, not §11 fixtures)

* `mr 6 sc` — **native** (`ring.R`, `(6sc)@R`; the parser calls the ring node `ring`, the
  exporter maps it to a chain).
* Increases — **native**: `sc@[@]` adds one stitch on the previous stitch without consuming a
  step target; `2sc@[@]` adds two on the same stitch; `Nsc@[@]` in general. This is exactly the
  `(2 sc in next)` construct.
* Tube base — same oval idiom as the bag.

## 3. Headless export (step 3)

`tools/crochet/cp_export.mjs` (committed) runs the parser and layout headlessly:

* **Parser:** `parse64.js` is loaded in a node `vm` context (`globalThis = this` shim; no
  window). `final(text)` returns the `Stitches` array — each stitch carries
  `id`/`id_attach` (top node ids / resolved attachment ids), `type`, `nrow`, `label`, `uid`,
  `topNodes`/`bottomNodes`, `connections`. `nrow` is assigned after `#` comments are stripped,
  so comment lines do not shift rows. The exporter also reads the global `LIST` (the parsed
  instruction list) to detect `turn` exactly, the way the parser does.
* **Layout (`--layout`):** `processText(text, '')` returns `[json, simpleDot]`; the simple DOT
  is line 1 = dimension, then node lines `"row,pos|uid"`, then edge lines `"a" -- "b" len`.
  `graph64.js` + `graph64.wasm` run in a second `vm` context; `Module.ccall('performLayout', …)`
  returns `{"name": "row,pos|uid","pos": "x,y,z"}` entries. The exporter maps the first node
  per stitch uid to `positions[id]`.
* **Mapping:** `sk` and `start_anew` are not stitches (no id) — skipped; `ring` → `ch`/`space`;
  `sc`/`scbl`/`scfl`/`fpsc`/`bpsc` → `sc` with loop `both`/`blo`/`flo`/`fpost`/`bpost`;
  `ss`/`ssbl`/`ssfl` → `slst`; targets = `id_attach` translated to exported ids; `prev` =
  previous exported stitch in creation order; `row` = `nrow`; `line` = the source line mapped
  through the non-comment lines. Output matches the §5.0 schema exactly
  (`stitches`/`rows`/`links`/`positions`/`errors`).

Usage:

```sh
node tools/crochet/cp_export.mjs [--layout] [--time] [--out FILE] PATTERN.txt
```

The checkout must be at `third_party/crochetparade` or `CP_DIR`; if missing, the tool exits
with clone instructions.

All ten fixtures export with **0 errors**: pouch 1380 stitches / 133 rows; each bag 5798 / 146
(surface: 5912 / 147); circles 217 / 189 / 273 stitches; tube 512.

## 4. Dump check (step 4)

| Field | Available? | Where it comes from |
|---|---|---|
| stitch **type** | yes | the stitch object's `type` (`ch`, `sc`, `scbl`, `ssbl`, `ss`, `sk`, `ring`, …) |
| **targets** (worked into) | yes | `id_attach`, resolved node ids; all fixture stitches have exactly one; `ch`s have none |
| **loop** | yes | the stitch family: `scbl`/`ssbl` → blo, `scfl` → flo, `fpsc`/`bpsc` → fpost/bpost, plain → both, `ch`/`ring` → space (BL/FL also carry jacobians in `bottomNodes`) |
| **prev** | yes, as creation order | CP has no "previous stitch" pointer; §5.0's "the stitch made just before it" is the previous stitch in file order, which the export emits (`prev = id − 1`) |
| **row / round** | yes | `nrow` |
| **source line** | yes | `nrow` mapped to the 1-based file line, comments excluded (verified: pouch border row `nrow 51` = `pouch.txt` line 58) |
| **turned vs round** | yes | a row is turned iff its last instruction is `turn` (pouch: 131 turned rows = foundation + 50 body + 80 strap; border and join are rounds) |

Examples (verbatim from the runs):

```json
{"id":0,   "type":"ch",   "piece":"main","row":0, "index":0, "loop":"space","targets":[],   "prev":-1,  "line":3}
{"id":840, "type":"sc",   "piece":"main","row":51,"index":25,"loop":"both", "targets":[14],"prev":839, "line":58}
{"id":378, "type":"slst", "piece":"main","row":4, "index":0, "loop":"blo",  "targets":[263],"prev":377,"line":9}
{"id":1379,"type":"slst", "piece":"main","row":132,"index":4,"loop":"both", "targets":[885],"prev":1378,"line":139}
```

Not available: `piece` (CP has no piece construct — the export writes `main`; the pouch's
body/border/strap and the bag's bag/strap are visible as row groups and can be segmented in
T4.1, or named by extension lines), `links` (no second targets — see step 2 workarounds), and
`sk`: it is a parser node used for stepping but not a stitch (its chain target is the stitch's
id). 1381 parser nodes in the pouch export as 1380 stitches because of it.

## 5. 3D layout (step 5)

Method: each test pattern is laid out cold (`processText` + `performLayout`); positions are one
per stitch. The layout is deterministic, and **idempotent**: feeding the positions back as the
input json makes them the fixed starting positions, and the result is exactly the input
(verified: one node moved by +2 in x comes out moved by +2, every other node 0.000000 — i.e. a
warm re-layout neither improves nor degrades the shape). Shape verdicts below use intrinsic
metrics, because the layout is not oriented by anything (no gravity, no floor):

* **plane fit** — best-fit plane of all nodes (covariance, smallest eigenvector; the Jacobi
  solver was verified with `A·v = λ·v`, orthonormal, 2e-13 on a test matrix); `rmsDev` = rms
  distance from that plane.
* **ring rms** — per round, the rms distance of the round's nodes from the round's own
  best-fit plane (0 = the round is a planar circle).
* **cone fit** — least squares `d = a + b·ρ` (plane distance vs in-plane radius); `b` = cup
  slope, residual = everything the cone does not explain.

Round radii (mean XY radius of each round, from round 1 to 8) and rim metrics:

| circle | radius per round | rim radius | rim ring rms | plane rmsDev | cone slope | cone residual | max\|z\| | max\|z\|/rim |
|---|---|---|---|---|---|---|---|---|
| +6 | 0.87, 1.63, 2.44, 3.22, 3.99, 4.77, 5.54, 6.32 | 6.32 | 0.94 | 0.83 | 0.02 | 0.83 | 6.11 | 0.97 |
| +5 | 0.64, 1.14, 1.71, 2.27, 2.80, 3.30, 3.79, 4.27 | 4.27 | 0.13 | 0.98 | −0.58 | 0.26 | 6.68 | 1.56 |
| +8 | 0.95, 1.71, 2.65, 3.54, 4.41, 5.27, 6.11, 6.94 | 6.94 | 2.90 | 2.21 | −0.04 | 2.21 | 6.03 | 0.87 |

* **+6 comes out flat.** Radius grows linearly (steps 0.77–0.81 per round = the constant-width
  ring a flat circle needs); the whole disc deviates from its best-fit plane by 0.83 rms ≈ 13 %
  of the rim radius, and every round is a near-planar circle (rim ring rms 0.94).
* **+5 comes out cup-shaped.** It is a smooth cone: `d ≈ −0.58·ρ` with a residual of only 0.26
  (≈ 6 % of the rim radius); the rounds are almost perfectly planar circles (ring rms 0.13),
  and the rim pulls in to 4.27 — 32 % smaller than the +6 rim — because the missing
  circumference goes into height. The radius steps shrink (0.50 → 0.48).
* **+8 comes out ruffled.** The rounds stop being planar: rim ring rms 2.90 (≈ 42 % of the rim
  radius), deviations from the cone fit wave around the rim (max ±2.4 vs the ±0.59 of +5),
  and the radius grows faster than +6 but less than a flat +8 ring would need — the excess
  circumference buckles out of plane in waves.

So the step-5 question is answered **yes for all three**, in the shape's own frame. The world
coordinates are arbitrary: all three discs are tilted about 45° relative to world z (that is
why raw `max|z|` is close to the radius for every circle, and why the ratio column above is
not a shape indicator). T5.3 will need to orient/constrain the initial layout.

**Tube (40 sts, 13 rounds):** the axis is straight (the round centers deviate 0.090 from the
end-to-end line = 1.1 % of its 8.43 length), rings are near-planar (last ring rms 0.59), but
the radius is not constant: 2.07, 2.53, 3.04, 3.55, 3.99, 4.29, 4.48, 4.58, 4.65, 4.70, 4.76,
4.90 — it grows and asymptotes instead of holding the base width, and `max|z|` = 8.27. It is
usable as an **initial** shape (rescaled, then our relaxation), not as a final cylinder; the
drift is worth a look when T5.3 wires CP positions in.

## 6. Timings (step 6)

Best of three runs, measured by the exporter itself (`--time`); layout time as reported
includes loading `graph64.wasm` on first use and building the layout input:

| pattern | stitches | parse | parse + layout (cold) |
|---|---|---|---|
| pouch | 1380 | 92 ms | 3.5 s |
| bag (plain) | 5798 | 665 ms | 66 s |
| circles / tube (single runs) | 217 / 189 / 273 / 512 | ~15 ms (+6) | 98 / 36 / 70 / 225 ms (solve only) |

The decision rule's bar — parsing the bag in under 2 s — is met by a wide margin (0.67 s). The
bag's *layout* is slow (66 s, single-threaded wasm; the solve dominates). Warm re-layout of the
same shape is the identity and returns in 13–60 ms, but a changed shape pays the full cost, so
T7.1 should run layout on a worker (the plan's `OS.execute` note) and/or cache results.

## 7. Decision input (step 7)

Against the plan's rule:

* **"All fixtures are expressible (workarounds are fine if the resulting stitch graph is
  right)"** — almost: everything parses with the right counts and targets, but the pouch's side
  seams (50 sts) and both strap-end joins (5 + 6 sts) are **one stitch with two working
  targets** in the DSL, and CP can only attach one. The second targets are exactly the §6.7
  point seams; the stitch graph is therefore *not* fully right without an addition.
* **"Step 4 gives type, targets, loop, prev and row for every stitch"** — yes, plus the source
  line and turned-vs-round (§4).
* **"Parsing the bag takes under 2 s"** — yes, 0.67 s (§6).

That is precisely the plan's **B** trigger ("the grammar works, but something essential is
missing — most likely through-both-layers"). **Recommendation: B — adopt CrochetPARADE and add
the missing piece as a Failoring extension line** that CP ignores (a `#!` comment line is a
comment to CP; comment lines do not shift rows) and our importer reads. Minimum content for the
extension, from this spike:

* the **second target** for a through-both-layers stitch or a join: for a seam/join stitch, name
  its partner target (our own addressing: piece/row/position). One line per stitch or a span
  form; the exact syntax is T4.1/T4.2's job (`docs/CROCHET_DSL.md`).
* optionally, **piece names** (body/border/strap) — CP has no piece construct and the export
  writes `main` for every stitch; row groups or `#!` lines can segment them in T4.1.

Not missing (verified): stitch graph extraction, stitch type, targets, loop, prev, row, source
line, turned/round, counts, increases/decreases, BLO/FLO/post, sl st rounds, joins, rings, and
a usable-if-rough 3D layout. The fold and the surface-sl st placement remain layout concerns
for T5.3, not grammar gaps. Nothing observed points to C.

Consequences (unchanged from the plan's A/B text): `patterns/cp/*.txt` replace the `.fcro`
fixtures; T4.1 = bridge/exporter + C++ importer into `StitchGraph` + the extension-line reader;
T4.2 = RS/WS facing, point seams from `links`, count checks; T5.3 may use CP positions as the
initial layout (with the caveats of §5).

## 8. How to reproduce

```sh
# once (the checkout is git-ignored):
git clone https://github.com/stassev/CrochetPARADE third_party/crochetparade
git -C third_party/crochetparade checkout 06e987b13ccfc94cfdfcebc1fe4664d37d2c6687

# export a fixture (JSON on stdout; --layout adds positions, --time prints timings to stderr):
node tools/crochet/cp_export.mjs patterns/cp/pouch.txt
node tools/crochet/cp_export.mjs --layout --time patterns/cp/circle_plus6.txt

# timings for the decision rule:
node tools/crochet/cp_export.mjs --time patterns/cp/bag_round_plain.txt
```

The shape metrics of §5 are defined there; they were computed from the `--layout` positions
(plane = covariance smallest eigenvector; cone = least squares on plane distance vs in-plane
radius; ring rms = per-round plane fit).

## 9. Limits / not verified

* No visual comparison against the CrochetPARADE web app was made; all numbers are headless.
* The Codeberg head was recorded, not re-fetched, in the final session.
* Timings are one machine (Apple Silicon, node 26.10.0) and not a benchmark; the layout numbers
  are deterministic, the wall-clock ones are not.
* The circles' verdicts are relative to each shape's best-fit frame; the layout does not orient
  the piece in world space (raw `max|z|` ≈ radius for every circle).
* The wall stitch graph was checked for counts/targets per row; it was not checked stitch by
  stitch against the plan's count comments beyond that.
